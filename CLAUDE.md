# Italian practice app — briefing for Claude

This repo (`grantgilford/ripasso-italiano`, renamed from `italian-practice` in Oct 2026) is the workshop for Grant's personal Italian practice app, **Ripasso Italiano** ("Ripasso" in the app). Read this file first in every session.

## What's here

- `index.html` — the whole app: one self-contained HTML file (vanilla JS and CSS, no build step). Content (units, items, lessons, the Verbs section `VERB_GYM`, `ID_ALIASES`, and from v9.6 `ITEM_SECTIONS`, the lesson section that teaches each item) is embedded as JS constants, laid out one entry per line (from v9.2): each pack's units and items one per line (a grammar unit's notes one per line), `LESSONS` one section per line, `VERB_GYM` one verb per line, `ID_ALIASES` one alias per line, `ITEM_SECTIONS` one unit per line. So a pull request shows a content change as the lines it changes; keep that layout (`check-content.js` reports a problem if it breaks, and `format-content.js` restores it). The version is `APP_VERSION` near the end of the file, with `CHANGES` beside it: that version's changes in one or two plain sentences, which Today shows once after an update ("What's new in 9.1", from v9.1).
- `docs/italian-app-spec.md` — the original build spec (goals, principles, exercise types, spaced repetition, screens), kept for history. Where it disagrees with the content guide, the design system or `docs/exercise-types.md`, they win.
- `docs/design-system.md` — the **Ripasso Italiano** look (Oct 2026): name, logo, colours, type, components and every screen, with mockups, logo files and fonts in `docs/design/`. Follow it for any interface work.
- `docs/italian-app-content-guide.md` — **the standard for all content work**. Every unit, item, explanation and lesson must meet it. Read it in full before touching content.
- `docs/exercise-types.md` — **the catalogue of exercise types**: every kind of exercise the app builds (from v8.6 also Spot the mistake, Complete the endings, Reply, Sort the words, Match the pairs, Listen and type, Make it plural), when each appears, which units could use the newer ones, ideas not yet built, and the checklist of every place a new type touches. Read it before choosing the mix of items for a unit, and before building a new type; add a row when you add one.
- `CHANGELOG.md` — one line per version, newest first, back to v7.3. Every version adds its line at the top (see How to work).
- `package.json` — the tools' one dependency, Playwright, pinned (the app itself needs nothing). `npm install` once per session, then `npm run check` (the content check), `npm test` (the content check, then the progress, interface, installed-copy, speed-ups, session, choices and speed tests, stopping at the first that fails) or `npm run test:items -- u19 u17` (the item test on those units; anything after `--` is passed on). The tools find Playwright in `node_modules` first, then a global install.
- `tools/lib/` — code the tools share: `load-app.js` loads the app's content into Node (for check-content, unit-items, add-items, edit-items, check-new-words, pack-levels, same-content, variety, link-sections and test-choices), `content-source.js` finds each content constant in `index.html` and writes it in the one-entry-per-line layout (for format-content, add-items, edit-items and check-content), `browser.js` finds Playwright, serves the app and counts checks (for the browser tests), and `seed.js` saves about 6,600 progress records in the page, a well-used device (for test-perf, test-speedups and test-sessions). Change a tool's loading or serving there, not in the tool.
- `tools/check-content.js` — the content checks (`node tools/check-content.js`, add `--verbose` for every finding), the lesson links in `ITEM_SECTIONS` (each names exactly one section by its heading, never a number, and every item of a unit with a lesson has one or `null`), that every transform has `en` (the English of its first answer) and every reply `lineEn` (the English of the other person's line), from 9.16, the release notes (`CHANGES` and the version's `CHANGELOG.md` line), and that the content keeps its one-entry-per-line layout. Reads `index.html` and `CHANGELOG.md` and changes nothing.
- `tools/format-content.js` — lays the content constants out one entry per line (`node tools/format-content.js`; `--check` only reports). Safe to rerun: it reads each constant as JSON and writes back the same values in the same order, so on a file already laid out it changes nothing.
- `tools/same-content.js` — checks that two copies of `index.html` hold the same content, however it is laid out (`node tools/same-content.js main`, or two paths or git refs; the second defaults to the `index.html` here). Deep-compares every capitalised content constant (`BUILTIN_PACKS`, `LESSONS`, `VERB_GYM`, `ID_ALIASES`, the tables the exercises use…) and what `buildContent()` makes of them, and lists each difference by its path; `APP_VERSION` and `CHANGES` are not compared. Run it against `main` after any change meant to leave the content alone (a reformat, a change to the tools or the code).
- `tools/variety.js` — the variety report (`node tools/variety.js [u01 …]`, about half a minute): builds every grammar item's exercise with the app's own `makeExercise` at boxes 1–4, eight times each, with a seeded random generator, and prints per unit how many kinds of exercise (`typeKey`) it gives and the shares of the two commonest, flagging fewer than 10 kinds or one kind above 35%, then each kind's share overall. `--markdown` prints the "Measured mix" section of `docs/exercise-types.md`; refresh that section after changing a unit's mix of items.
- `tools/link-sections.js` — proposes, for each item of a unit with a lesson, the section that teaches it (`node tools/link-sections.js [u01 …]`, a few seconds): it scores each section of the item's unit (BM25) by the item's Italian (answers, forms, cloze blanks, fixes), the Italian words of its explanation and its English, and prints the best with a confidence, beside the link stored in `ITEM_SECTIONS`. `--low` lists the proposals to review by hand (confidence under 0.5), `--missing` the items with no link, `--diff` those stored differently, `--json` one object per item, and `--write` stores the proposal for items with no link (never changing a stored one). Its proposals match the hand-reviewed links in `ITEM_SECTIONS` four times in five (nine in ten at a confidence of 0.5 or more, two in three below), so review every proposal under 0.5 by hand, and link to another unit's section where that is where the rule is taught.
- `tools/unit-items.js` — prints a unit's items readably (`node tools/unit-items.js u01`, `--type spot` for one type, `--json` as stored), every card and sentence that uses a word (`--word casa`, with the full data a copy in another unit must match to share progress), and how many items of each type every unit has (`--counts`). Reads `index.html` and changes nothing.
- `tools/add-items.js` — adds new items to `index.html` from a JSON file (`node tools/add-items.js items.json`, `--dry-run` first), each as one line after the last item of its unit, in whichever pack holds the unit (the grammar units, u18 or a vocab pack; not the Verbs section, which is built from `VERB_GYM`); refuses existing ids and anything the app's own pack check rejects. An item of a unit with a lesson needs a `"section"` (the start of the heading of the section that teaches it, `"uXX#…"` for another unit's, or `null`), which it writes to `ITEM_SECTIONS` rather than onto the item. Write new content in a scratch JSON file and add it with this rather than editing the content lines by hand.
- `tools/edit-items.js` — changes and removes existing items: `node tools/edit-items.js --replace items.json` replaces each item by its id, where it stands (each item in full, as it will be stored; refuses unknown ids), (an item may carry `"section"`, its new lesson link) and `--remove ID --to NEWID` deletes an item, with its lesson link, and adds `ID_ALIASES[ID] = NEWID` so its progress moves to NEWID (refuses when NEWID isn't an item; an alias that pointed at ID is pointed at NEWID too). Both take `--dry-run` (which prints the old and new lines), run the app's own pack check and refuse what it rejects, write one item per line, and warn when a change stops an item sharing progress with its copies in other units. Use it rather than editing item lines by hand; afterwards run the content check, the item test on the units changed and the progress test.
- `tools/check-new-words.js` — checks a list of candidate words for a new vocab pack against every word already in the app (`node tools/check-new-words.js words.txt`), so a pack adds only new words. The flashcard packs run from pack 1 (common words) to pack 9 (upper-intermediate), in order of difficulty; a pack's number comes from how common its words are, not from its unit id (pack 2 is unit `fc07`, pack 5 is `fc06`, pack 7 is `fc09`, pack 8 is `fc08`, pack 9 is `fc05`), and each later pack should be a gentle step up.
- `tools/pack-levels.js` — how common each vocab pack's words are (`node tools/pack-levels.js`), the same for a draft list (`… words.txt`), and the most common words no card has yet (`… --missing 1 3000`). It reads `tools/word-ranks.txt`, about 20,000 Italian words in order of frequency, and counts a verb form as its verb. Use it to choose a new pack's words, to number it among the others and to order its cards (other scripts can load its `rankOf`).
- `tools/test-items.js` — the item test (`node tools/test-items.js u19 [u17 …] [--ids a,b] [--repeats 4]`, a few minutes per unit, longer for a big one; `--repeats 2` is quicker; needs Playwright and Chromium). Builds every exercise the named units' items can produce, as new, half-learned and learned items, and answers each one right through the real screen, as a learner would by tapping and typing; it fails if a right answer is marked wrong, is missing from the options offered, or a script error occurs. Run it on every unit you add items to.
- `tools/test-progress.js` — the progress safety test (`node tools/test-progress.js`, about a minute; needs Playwright and Chromium). Runs the real app in a headless browser and checks that saved progress, in the browser and in the synced copy, survives loading, aliases, practice sessions, syncing and a new device; that a record for every item in the course fits (each cloud document under 200 KB, the limit being 256 KB, and the browser copy under 3 MB, both printed); that damaged records are repaired or left out in the browser copy, a backup file and the cloud's shards (from 9.4); and that only what changed is written to the cloud. `tools/item-ids.txt` lists every id that may hold progress.
- `manifest.webmanifest`, `sw.js`, `icons/`, `.nojekyll` — what turns `index.html` into an installable phone app when the repo is served from its own website (GitHub Pages, see below). `sw.js` is the offline worker: it keeps a copy of the app on the device and fetches new versions in the background. It finds a new version by comparing `index.html` itself, so a release needs no change to `sw.js`.
- `tools/test-install.js` — the installed-copy test (`node tools/test-install.js`, about 30 seconds; needs Playwright and Chromium). Serves the repo like GitHub Pages and checks the manifest and icons, opening offline, the update prompt (offered on Today, never mid-session, keeping progress; checked on opening, and on coming back only if the last check was over three hours ago), the back button, the backup cards and buttons, and that none of it runs inside claude.ai.
- `tools/test-ui.js` — the interface test (`node tools/test-ui.js`, about three minutes; needs Playwright and Chromium). Tours every screen by tapping, in light and dark at 390 and 360 px wide and at 120% text, and checks the design system's rules: every screen reachable, choosing a unit on Units (any card opens with Practise and Read lesson, and Today's Continue card follows the unit practised last), no script errors or outside loads, nothing hidden behind the tab bar, 44 px tap targets, the answer panel, the Appearance setting, the "Lo sapevi?" card, room above the keyboard (on typed questions Don't know and Check must clear a Pixel 8's keyboard, so keep the session screen compact), the exercise types added in v8.6, each answered right and wrong by tapping and typing (`newTypes`), English answers with contractions (*I'm* = *I am*), the "What's new" card (shown after the version changes, in every copy, until Got it), Read the rule and Practise this section (from 9.6: when the answer panel offers the rule, the sheet it opens over the session drawn as the lesson draws it, scrolling inside, closed by Close, a tap beside it, Escape and the back button with the session left exactly as it was, links and speakers in it, and the buttons at the end of each lesson section), and read aloud (with a stand-in voice: every speaker reads its Italian, a prompt's speaker never gives the answer away on any item, Listen and type plays only the item's own sentence without showing it, and the speakers hide where there is no Italian voice or no speech).
- `tools/test-perf.js` — the speed test (`node tools/test-perf.js`, about two minutes; needs Playwright and Chromium). Opens the app at 390 × 844 with the CPU slowed 4× and about 6,600 progress records saved, and times a reload to Today, the word lists built in idle time after it (and the longest slice of that work, which must stay under 50 ms), `buildContent`, a cold `knownWords()`, the counts worked out afresh, drawing the busiest screens, opening a verb, the filters, Look up keystrokes (each until its results are drawn), `buildSession` for every kind, the first lookup of a flashcard's sentence (from 9.7, held to the same 50 ms as a slice of idle work), and the sync with a stand-in database: `pushProgress` comparing everything, after an answer and after a snapshot that only echoes its writes, the echo itself, and another device's copy merged in (`adoptRemote` and a whole snapshot). It prints a table and fails when a figure is over its budget. The budgets are one table at the top of the file, set at v9.3 to the slowest of five runs plus 25%, or the 9.1 budget where lower (the 50 ms limit on a slice of idle work is fixed); when a change makes something faster, lower its budget (`--new-budgets` prints this run's figures plus 25%). If every figure is over by about the same amount, suspect a slower computer, not the change: run it on the previous version's `index.html` too (it takes a path, and runs on 9.2 and before, leaving out the figures they can't give) and compare. It is part of `npm test` but **not** of the GitHub workflow, because the shared computers GitHub runs on vary in speed; so run it yourself after any change to the app's code (not needed for content-only changes, though a big new pack is worth a run).
- `tools/test-sessions.js` — the session test (`node tools/test-sessions.js`, about a minute; needs Playwright and Chromium). How grammar sessions are put together (from 9.5), with about 6,600 progress records and a seeded random generator: built many times, no kind of exercise three times in a row where the mix allows, at least four kinds in 12 exercises where the items can give them, and the same share of typed exercises as without the session's hint (which never changes an exercise's kind); the per-device memory of each item's last kind (`itapp.lasttype.v1`: kept out of progress, capped, damaged values and refused storage harmless) and the next session giving another kind; the spread of reviews at box 3 and above (within 10%); tricky items introduced again, the introduction leaving the record alone and the typed follow-up moving it, and listed on Stats; the 7-day forecast against `dueIds()`; Another round after every kind of session, disabled when nothing is left; and (from 9.6) new items taken in the order of the lesson's sections, and Practise this section's sessions (only the section's items: due, then new within today's limit, then the rest). Run it after any change to `buildSession`, `sessionIds`, `planSession`, `makeExercise`'s choices, `applyResult`, the summary or Stats.
- `tools/test-choices.js` — the choices test (`node tools/test-choices.js`, about a minute; needs Playwright and Chromium for its second half). Wrong options and answer panels that teach (from 9.7). In Node, over the whole content: every word order near-miss (`nearMisses`: another person of the sentence's verb in the same tense, the other article of the same number, another form of an adjective) is a form the content or `VERB_GYM` states and, put in place of any word or added anywhere, never makes a sentence `checkAnswer` accepts against `translationsOf()` or word order accepts, is offered as one of the two extra words and named in the answer panel; meaning choices (`distractorsFor`), both ways, with and without remembered mix-ups, never offer a right answer, a word with the same Italian or one sharing the meaning asked for, offer one option per word and remembered mix-ups first; no multiple choice of any grammar-unit item offers one of its answers as a wrong option; about 660 cards have a grammar-unit sentence with their word (`contextFor`); and (from 9.16) every exercise of every item shows its English, asks for it, or gives it in the answer panel (`ex.meaning`: the verb of a conjugation, the noun of an article or plural drill, the Verbs section's Which verb?, Which person?, Which tense? and Change the tense, Listen and type, a transform's `en`, a reply's `lineEn`…), the item's own English. In the browser: the confusion memory (`itapp.confusions.v1`: a chosen meaning, a typed word and a typed card each recorded as a pair, "You've mixed up X and Y N times" from the second time, surviving a reload, Accept my answer taking it back, kept out of progress, the backup and the cloud, capped at 500, damaged values and refused storage harmless), a word order trap on the screen, a flashcard's sentence in the answer panel (the word in bold, its English, a speaker that reads it), and the meaning in the answer panel, right and wrong, for a conjugation, a transform, a reply and Listen and type. Run it after any change to word order, meaning choices, the confusion memory, the flashcard sentences, the answer panel's reasons or its meanings.
- `tools/test-speedups.js` — the speed-ups test (`node tools/test-speedups.js`, about half a minute; needs Playwright and Chromium). What the app keeps ready to be quick (from 9.3) must give exactly what the plain code gave, which it keeps a copy of (as in 9.2) to compare against: Look up, a unit's glossary filter and the Verbs filter for 30 queries (the same items in the same order, the same lesson sections, the same results drawn, and typing that redraws only the results); the Verbs reference (tables drawn when a row opens, each row as 9.2 drew it); every count on Today, Units, Stats and You, on seeded progress, as time passes and after an answer, an undo, a setting, a sync merge, a backup and a reset; the word lists, gloss index and (from 9.6) lesson sections built in idle time; start-up saving only when loading changed the progress; and the sync merge (from 9.4, record by record in place) against 9.3's mergeProgress and buildContent, case by case. Run it after any change to search, the counts, the Verbs reference or the idle-time work; when a change is meant to alter what one of these shows, change the copy of the plain code in the test with it.
- `.github/workflows/checks.yml` — the automatic checks: on every pull request and every push to `main`, GitHub runs the content check and the progress, interface, installed-copy, speed-ups, session and choices tests (Node 22, Playwright with Chromium), each as its own step, and the run fails if any of them does. A pull request shows a green tick or a red cross; a red cross must be fixed before Grant merges.
- `.github/workflows/release.yml` — on every push to `main` (a merge), reads `APP_VERSION` and tags that commit `v<version>` if the tag doesn't exist yet, with its CHANGELOG line as the message.

## How the app reaches Grant

The app reaches Grant in two ways, both from the same `index.html`:

1. **The claude.ai artifact** (https://claude.ai/artifact/1d1Zqo9n8UtXgizSuxjVnJ), with cloud sync. After work here is merged, Grant republishes `index.html` to that link from a claude.ai chat.
2. **The installed copy** (from version 8.1): GitHub Pages serves the `main` branch at https://grantgilford.github.io/ripasso-italiano/, and Grant installs it on his Android phone from Chrome. **Merging to `main` publishes it**: the installed app finds the new `index.html` the next time it opens and offers it on Today ("Update now"). Its progress is kept on the device only (no cloud sync), with backup files to move it between copies.

So:

- Never try to publish or deploy anything yourself, and don't merge to `main`. Your job ends with a tested `index.html` on a branch.
- `index.html` must keep working as a single self-contained file, both on claude.ai and opened straight from disk. Don't split it into several files, add a build step, or load anything except pinned scripts from cdnjs. The files beside it (manifest, worker, icons) are only for the installed copy, and the app only uses them when served from its own website (`HOSTED` in the code: outside claude.ai, over https or on localhost). Inside claude.ai (`IN_CLAUDE`) none of the installed-copy code runs: no manifest, no worker, no history entries, no notices.
- Outside claude.ai the Android back button is handled with one extra history entry while away from Today (`syncHistory()`); in a session, back asks before leaving. A new screen with a header back arrow (`screenHead(…, { back })`) is handled automatically.
- **Progress is kept in two places, and both hold Grant's real progress:**
  - **The browser copy**, in localStorage: `itapp.progress.v1` (progress), `itapp.packs.v1` (imported packs), `itapp.reading.v1` (last lesson section read) and `itapp.migratedV1` (a one-time flag). `itapp.theme.v1` (Appearance: `"light"`, `"dark"` or `"auto"`) is a per-device preference, deliberately kept out of progress so it never syncs; it is read by a small script in `<head>` before the first paint. `itapp.backup.v1` (`{ at, snooze, welcomed }`: the last backup made on this device, the backup reminder's snooze, and whether the first-run card was dismissed) is per-device too and never synced, as is `itapp.audio.v1` (Read aloud: `"off"`, `"normal"` or `"slow"`; from v8.2), since each phone has its own voices, `itapp.seen.v1` (the `APP_VERSION` whose "What's new" card this device has dismissed, as a string such as `"9.1"`; from v9.1; a device with no progress yet starts with the current version, so a first visit gets no card), and `itapp.lasttype.v1` (from v9.5: the kind of exercise, `typeKey`, each grammar item was last answered with on this device, as a list of `[record id, typeKey]` pairs, oldest first, at most 2,000; the session uses it to give the item another kind next time), and `itapp.confusions.v1` (from v9.7: pairs of items mixed up on this device, as a list of `[record id, record id, times]`, the two ids in order, the pair mixed up last at the end, at most 500; meaning choices offer the other word first and the answer panel says "You've mixed up X and Y N times" from the second time).
  - **The synced copy**, in the artifact's cloud database (`window.claude.use("db")`), which carries progress across devices: `progress2/meta`, `progress2/days_YYYY`, the item shards `progress2/s00`…`s15` (each record packed as a fixed-order array), plus `flags/<id>` and `packs/<id>`. The old `progress/main` document is still read once per device for migration.

  The counts on Today, Units, Stats and You are kept between visits (`counts()`, from 9.3) until `saveProgress()` or `buildContent()` drops them or time changes one, so code that changes progress must go on calling `saveProgress()` afterwards (as all of it does), or those screens show the numbers from before. From 9.4 it must also mark what it changed for the cloud (`DIRTY`): `markItem(id)` for a record, `markDay(day)` for the daily log (`today()` marks it for whoever asks), and `saveProgress()` marks meta; code that replaces progress wholesale sets `DIRTY = null`, so the next push compares every document. An unmarked change still reaches the cloud, but only when the app is put away (that push compares everything). Every record read from storage (the browser copy, a backup, the cloud's shards, either side of a merge) goes through `checkRec`, which repairs or drops a damaged one; keep it that way for any new way in. Word lists and indexes taken from the content (`KNOWN_WORDS`, `GLOSS`, the search index, from 9.6 `SECTIONS`, each item's lesson section, and from 9.7 `NEAR`, the forms word order traps are found with, and `ANSWERS`, every word's Italian for the confusion memory) are built while the phone is idle; their `*Steps` generators must yield after each small step so no slice runs over 50 ms (`test-perf.js` measures it). `CONTEXT` (9.7, the grammar units' sentences by word, for the flashcard sentences) is built when a card first needs one instead, held to the same 50 ms; `buildContent()` drops them all when the content changes.

  Never rename a key, collection or document, change the shard count or hashing, reorder the packed record, or otherwise change either format without a migration that reads the old format. The two copies are merged on every load, so a change to one must keep the merge with the other working, and a mistake in either loses progress on every device. When an item is removed or renamed, map its old id in `ID_ALIASES`.

## How to work

1. Work on a new branch, never directly on `main`. Grant reviews and merges.
2. Bump `APP_VERSION` (7.2 → 7.3, and so on) for any change that will be republished, and update the version mentioned in the content guide's first paragraph if the guide changes. Every version also says what changed, twice: replace `CHANGES` beside `APP_VERSION` with this version's changes in one or two plain sentences for Grant (Today shows them once, as "What's new"), and add the version's line at the top of `CHANGELOG.md` (`- **9.2** (date): …`). `check-content.js` reports a problem until both are done.
3. Before finishing, run the checks (after `npm install`, `npm test` runs the content check and the progress, interface, installed-copy, speed-ups, session, choices and speed tests in one go). Run `node tools/check-content.js`. It checks that the script parses and runs the content checks the guide describes (lesson links resolve, every wrong option has a note, verb forms agree with `VERB_GYM` and the regular rules, and more). It must report no problems; read its "worth a look" list and deal with anything your change added. Then run `node tools/test-progress.js`: every check must pass. For any change to the interface, also run `node tools/test-ui.js` (every check must pass), and for any change to navigation, backups, the installed-copy code or the files beside `index.html`, run `node tools/test-install.js` too; for any change to search, the counts on Today, Units, Stats and You, the Verbs reference or the work done in idle time, run `node tools/test-speedups.js`; for any change to how sessions are built, how exercises are chosen, scheduling, the summary or Stats, run `node tools/test-sessions.js`; for any change to the wrong options an exercise offers (word order's extra words, meaning choices), the confusion memory, the flashcard sentences or the reasons in the answer panel, run `node tools/test-choices.js`. If you add items, run `node tools/test-items.js` on the units you added them to, and run the progress test with `--update-ids` to add their ids to `tools/item-ids.txt`; if the progress test reports a missing id, an item was removed or renamed without an `ID_ALIASES` entry, so add one rather than editing the list. After a change meant to leave the content alone (to the tools, the code or the layout), run `node tools/same-content.js main`: it must find no difference. If you deliberately change a storage format, write the migration first and then update the test to the new format in the same branch. After any change to the app's code, run `node tools/test-perf.js` too: every figure must stay within its budget (it isn't in the GitHub workflow, so nothing else catches a slowdown). Where a check isn't scripted yet, add it to these scripts (or a new one under `tools/`) and commit it, so the next session can reuse it. Once the branch is pushed and a pull request is open, GitHub runs the same checks (`checks.yml`); if a step fails there, fix it.
4. If a change alters how the app treats content, update `docs/italian-app-content-guide.md` in the same branch.
5. End with a short summary for Grant: what changed, the new version number, and anything he should check on his phone.

## Writing style

British English throughout, as the content guide sets out. Plain, concise explanations. Grant is learning Italian at roughly A1–A2 level and isn't a programmer: summaries for him should be in plain language.

## Safety net

The tag `v7.2` marks the known-good starting version. From 9.1 every version that reaches `main` gets its own tag (`v9.1`, `v9.2`…, made by `release.yml`), so `index.html` at any released version can be restored. If anything goes wrong, return to the last good version's tag, or to `v7.2`.
