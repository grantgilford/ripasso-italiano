# Italian practice app — briefing for Claude

This repo (`grantgilford/ripasso-italiano`, renamed from `italian-practice` in Oct 2026) is the workshop for Grant's personal Italian practice app, **Ripasso Italiano** ("Ripasso" in the app). Read this file first in every session.

## What's here

- `index.html` — the whole app: one self-contained HTML file (vanilla JS and CSS, no build step). Content (units, items, lessons, the Verbs section `VERB_GYM`, `ID_ALIASES`) is embedded as JS constants. The version is `APP_VERSION` near the end of the file, with `CHANGES` beside it: that version's changes in one or two plain sentences, which Today shows once after an update ("What's new in 9.1", from v9.1).
- `docs/italian-app-spec.md` — the original build spec (goals, principles, exercise types, spaced repetition, screens), kept for history. Where it disagrees with the content guide, the design system or `docs/exercise-types.md`, they win.
- `docs/design-system.md` — the **Ripasso Italiano** look (Oct 2026): name, logo, colours, type, components and every screen, with mockups, logo files and fonts in `docs/design/`. Follow it for any interface work.
- `docs/italian-app-content-guide.md` — **the standard for all content work**. Every unit, item, explanation and lesson must meet it. Read it in full before touching content.
- `docs/exercise-types.md` — **the catalogue of exercise types**: every kind of exercise the app builds (from v8.6 also Spot the mistake, Complete the endings, Reply, Sort the words, Match the pairs, Listen and type, Make it plural), when each appears, which units could use the newer ones, ideas not yet built, and the checklist of every place a new type touches. Read it before choosing the mix of items for a unit, and before building a new type; add a row when you add one.
- `CHANGELOG.md` — one line per version, newest first, back to v7.3. Every version adds its line at the top (see How to work).
- `package.json` — the tools' one dependency, Playwright, pinned (the app itself needs nothing). `npm install` once per session, then `npm run check` (the content check), `npm test` (the content check, then the progress, interface, installed-copy and speed tests, stopping at the first that fails) or `npm run test:items -- u19 u17` (the item test on those units; anything after `--` is passed on). The tools find Playwright in `node_modules` first, then a global install.
- `tools/lib/` — code the tools share: `load-app.js` loads the app's content into Node (for check-content, unit-items, add-items, check-new-words and pack-levels) and `browser.js` finds Playwright, serves the app and counts checks (for the browser tests). Change a tool's loading or serving there, not in the tool.
- `tools/check-content.js` — the content checks (`node tools/check-content.js`, add `--verbose` for every finding), and the release notes (`CHANGES` and the version's `CHANGELOG.md` line). Reads `index.html` and `CHANGELOG.md` and changes nothing.
- `tools/unit-items.js` — prints a unit's items readably (`node tools/unit-items.js u01`, `--type spot` for one type, `--json` as stored), every card and sentence that uses a word (`--word casa`, with the full data a copy in another unit must match to share progress), and how many items of each type every unit has (`--counts`). Reads `index.html` and changes nothing.
- `tools/add-items.js` — adds new items to `index.html` from a JSON file (`node tools/add-items.js items.json`, `--dry-run` first), each as one line after the last item of its unit; refuses existing ids and anything the app's own pack check rejects. Write new content in a scratch JSON file and add it with this rather than editing the long content lines by hand.
- `tools/check-new-words.js` — checks a list of candidate words for a new vocab pack against every word already in the app (`node tools/check-new-words.js words.txt`), so a pack adds only new words. The flashcard packs run from pack 1 (common words) to pack 8 (upper-intermediate), in order of difficulty; a pack's number comes from how common its words are, not from its unit id (pack 2 is unit `fc07`, pack 5 is `fc06`, pack 7 is `fc08`), and each later pack should be a gentle step up.
- `tools/pack-levels.js` — how common each vocab pack's words are (`node tools/pack-levels.js`), the same for a draft list (`… words.txt`), and the most common words no card has yet (`… --missing 1 3000`). It reads `tools/word-ranks.txt`, about 20,000 Italian words in order of frequency, and counts a verb form as its verb. Use it to choose a new pack's words, to number it among the others and to order its cards (other scripts can load its `rankOf`).
- `tools/test-items.js` — the item test (`node tools/test-items.js u19 [u17 …] [--ids a,b] [--repeats 4]`, a few minutes per unit, longer for a big one; `--repeats 2` is quicker; needs Playwright and Chromium). Builds every exercise the named units' items can produce, as new, half-learned and learned items, and answers each one right through the real screen, as a learner would by tapping and typing; it fails if a right answer is marked wrong, is missing from the options offered, or a script error occurs. Run it on every unit you add items to.
- `tools/test-progress.js` — the progress safety test (`node tools/test-progress.js`, about a minute; needs Playwright and Chromium). Runs the real app in a headless browser and checks that saved progress, in the browser and in the synced copy, survives loading, aliases, practice sessions, syncing and a new device. `tools/item-ids.txt` lists every id that may hold progress.
- `manifest.webmanifest`, `sw.js`, `icons/`, `.nojekyll` — what turns `index.html` into an installable phone app when the repo is served from its own website (GitHub Pages, see below). `sw.js` is the offline worker: it keeps a copy of the app on the device and fetches new versions in the background. It finds a new version by comparing `index.html` itself, so a release needs no change to `sw.js`.
- `tools/test-install.js` — the installed-copy test (`node tools/test-install.js`, about 30 seconds; needs Playwright and Chromium). Serves the repo like GitHub Pages and checks the manifest and icons, opening offline, the update prompt (offered on Today, never mid-session, keeping progress), the back button, the backup cards and buttons, and that none of it runs inside claude.ai.
- `tools/test-ui.js` — the interface test (`node tools/test-ui.js`, about three minutes; needs Playwright and Chromium). Tours every screen by tapping, in light and dark at 390 and 360 px wide and at 120% text, and checks the design system's rules: every screen reachable, choosing a unit on Units (any card opens with Practise and Read lesson, and Today's Continue card follows the unit practised last), no script errors or outside loads, nothing hidden behind the tab bar, 44 px tap targets, the answer panel, the Appearance setting, the "Lo sapevi?" card, room above the keyboard (on typed questions Don't know and Check must clear a Pixel 8's keyboard, so keep the session screen compact), the exercise types added in v8.6, each answered right and wrong by tapping and typing (`newTypes`), English answers with contractions (*I'm* = *I am*), the "What's new" card (shown after the version changes, in every copy, until Got it), and read aloud (with a stand-in voice: every speaker reads its Italian, a prompt's speaker never gives the answer away on any item, Listen and type plays only the item's own sentence without showing it, and the speakers hide where there is no Italian voice or no speech).
- `tools/test-perf.js` — the speed test (`node tools/test-perf.js`, about two minutes; needs Playwright and Chromium). Opens the app at 390 × 844 with the CPU slowed 4× and about 6,600 progress records saved, and times a reload to Today, `buildContent`, a cold `knownWords()`, drawing the busiest screens, Look up keystrokes, `buildSession` for every kind, and `pushProgress` / `adoptRemote` with a stand-in database. It prints a table and fails when a figure is over its budget. The budgets are one table at the top of the file, set at v9.1 to that day's figures plus 25%; when a change makes something faster, lower its budget (`--new-budgets` prints this run's figures plus 25%). If every figure is over by about the same amount, suspect a slower computer, not the change: run it on the previous version's `index.html` too (it takes a path) and compare. It is part of `npm test` but **not** of the GitHub workflow, because the shared computers GitHub runs on vary in speed; so run it yourself after any change to the app's code (not needed for content-only changes, though a big new pack is worth a run).
- `.github/workflows/checks.yml` — the automatic checks: on every pull request and every push to `main`, GitHub runs the content check and the progress, interface and installed-copy tests (Node 22, Playwright with Chromium), each as its own step, and the run fails if any of them does. A pull request shows a green tick or a red cross; a red cross must be fixed before Grant merges.
- `.github/workflows/release.yml` — on every push to `main` (a merge), reads `APP_VERSION` and tags that commit `v<version>` if the tag doesn't exist yet, with its CHANGELOG line as the message.

## How the app reaches Grant

The app reaches Grant in two ways, both from the same `index.html`:

1. **The claude.ai artifact** (https://claude.ai/artifact/1d1Zqo9n8UtXgizSuxjVnJ), with cloud sync. After work here is merged, Grant republishes `index.html` to that link from a claude.ai chat.
2. **The installed copy** (from version 8.1): GitHub Pages serves the `main` branch at https://grantgilford.github.io/ripasso-italiano/, and Grant installs it on his Android phone from Chrome. **Merging to `main` publishes it**: the installed app finds the new `index.html` the next time it opens and offers it on Today ("Update now"). Its progress is kept on the device only (no cloud sync), with backup files to move it between copies.

So:

- Never try to publish or deploy anything yourself, and don't merge to `main`. Your job ends with a tested `index.html` on a branch.
- `index.html` must keep working as a single self-contained file, both on claude.ai and opened straight from disk. Don't split it into several files, add a build step, or load anything except pinned scripts from cdnjs. The files beside it (manifest, worker, icons) are only for the installed copy, and the app only uses them when served from its own website (`HOSTED` in the code: outside claude.ai, over https or on localhost). Inside claude.ai (`IN_CLAUDE`) none of the installed-copy code runs: no manifest, no worker, no history entries, no notices.
- Outside claude.ai the Android back button is handled with one extra history entry while away from Today (`syncHistory()`); in a session, back asks before leaving. A new screen with a header back arrow (`screenHead(…, { back })`) is handled automatically.
- **Progress is kept in two places, and both hold Grant's real progress:**
  - **The browser copy**, in localStorage: `itapp.progress.v1` (progress), `itapp.packs.v1` (imported packs), `itapp.reading.v1` (last lesson section read) and `itapp.migratedV1` (a one-time flag). `itapp.theme.v1` (Appearance: `"light"`, `"dark"` or `"auto"`) is a per-device preference, deliberately kept out of progress so it never syncs; it is read by a small script in `<head>` before the first paint. `itapp.backup.v1` (`{ at, snooze, welcomed }`: the last backup made on this device, the backup reminder's snooze, and whether the first-run card was dismissed) is per-device too and never synced, as is `itapp.audio.v1` (Read aloud: `"off"`, `"normal"` or `"slow"`; from v8.2), since each phone has its own voices, and `itapp.seen.v1` (the `APP_VERSION` whose "What's new" card this device has dismissed, as a string such as `"9.1"`; from v9.1; a device with no progress yet starts with the current version, so a first visit gets no card).
  - **The synced copy**, in the artifact's cloud database (`window.claude.use("db")`), which carries progress across devices: `progress2/meta`, `progress2/days_YYYY`, the item shards `progress2/s00`…`s15` (each record packed as a fixed-order array), plus `flags/<id>` and `packs/<id>`. The old `progress/main` document is still read once per device for migration.

  Never rename a key, collection or document, change the shard count or hashing, reorder the packed record, or otherwise change either format without a migration that reads the old format. The two copies are merged on every load, so a change to one must keep the merge with the other working, and a mistake in either loses progress on every device. When an item is removed or renamed, map its old id in `ID_ALIASES`.

## How to work

1. Work on a new branch, never directly on `main`. Grant reviews and merges.
2. Bump `APP_VERSION` (7.2 → 7.3, and so on) for any change that will be republished, and update the version mentioned in the content guide's first paragraph if the guide changes. Every version also says what changed, twice: replace `CHANGES` beside `APP_VERSION` with this version's changes in one or two plain sentences for Grant (Today shows them once, as "What's new"), and add the version's line at the top of `CHANGELOG.md` (`- **9.2** (date): …`). `check-content.js` reports a problem until both are done.
3. Before finishing, run the checks (after `npm install`, `npm test` runs the content check and the progress, interface, installed-copy and speed tests in one go). Run `node tools/check-content.js`. It checks that the script parses and runs the content checks the guide describes (lesson links resolve, every wrong option has a note, verb forms agree with `VERB_GYM` and the regular rules, and more). It must report no problems; read its "worth a look" list and deal with anything your change added. Then run `node tools/test-progress.js`: every check must pass. For any change to the interface, also run `node tools/test-ui.js` (every check must pass), and for any change to navigation, backups, the installed-copy code or the files beside `index.html`, run `node tools/test-install.js` too. If you add items, run `node tools/test-items.js` on the units you added them to, and run the progress test with `--update-ids` to add their ids to `tools/item-ids.txt`; if the progress test reports a missing id, an item was removed or renamed without an `ID_ALIASES` entry, so add one rather than editing the list. If you deliberately change a storage format, write the migration first and then update the test to the new format in the same branch. After any change to the app's code, run `node tools/test-perf.js` too: every figure must stay within its budget (it isn't in the GitHub workflow, so nothing else catches a slowdown). Where a check isn't scripted yet, add it to these scripts (or a new one under `tools/`) and commit it, so the next session can reuse it. Once the branch is pushed and a pull request is open, GitHub runs the same checks (`checks.yml`); if a step fails there, fix it.
4. If a change alters how the app treats content, update `docs/italian-app-content-guide.md` in the same branch.
5. End with a short summary for Grant: what changed, the new version number, and anything he should check on his phone.

## Writing style

British English throughout, as the content guide sets out. Plain, concise explanations. Grant is learning Italian at roughly A1–A2 level and isn't a programmer: summaries for him should be in plain language.

## Safety net

The tag `v7.2` marks the known-good starting version. From 9.1 every version that reaches `main` gets its own tag (`v9.1`, `v9.2`…, made by `release.yml`), so `index.html` at any released version can be restored. If anything goes wrong, return to the last good version's tag, or to `v7.2`.
