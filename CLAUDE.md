# Italian practice app — briefing for Claude

This repo (`grantgilford/ripasso-italiano`, renamed from `italian-practice` in Oct 2026) is the workshop for Grant's personal Italian practice app, **Ripasso Italiano** ("Ripasso" in the app). Read this file first in every session.

## What's here

- `index.html` — the whole app: one self-contained HTML file (vanilla JS and CSS, no build step). Its scripts, in order: a snippet in `<head>` that sets the theme before the first paint; **the storage script** (from 9.26: it defines `Store`, the only way saved data is read or written; its opening comment is the reference for what it offers, where things are kept, the move from localStorage and the two-window rules); a snippet that keeps script errors; and the app's script, which starts in `boot()` once `Store.ready` is kept. Content (units, items, lessons, the Verbs section `VERB_GYM`, `ID_ALIASES`, from v9.6 `ITEM_SECTIONS`, the lesson section that teaches each item, and from v9.20 `VERB_SENTENCES`, the Verbs section's example sentences) is embedded as JS constants, laid out one entry per line (from v9.2): each pack's units and items one per line (a grammar unit's notes one per line), `LESSONS` one section per line, `VERB_GYM` and `VERB_SENTENCES` one verb per line, `ID_ALIASES` one alias per line, `ITEM_SECTIONS` one unit per line. So a pull request shows a content change as the lines it changes; keep that layout (`check-content.js` reports a problem if it breaks, and `format-content.js` restores it). The version is `APP_VERSION` near the end of the file, with `CHANGES` beside it: that version's changes in one or two plain sentences, which Today shows once after an update ("What's new in 9.1", from v9.1). Beside them, `REPORT_TO` (from 9.19) says where reports from the app go: `{ github: "grantgilford/ripasso-italiano", email: "" }`, this repository's issue forms and, if set, an email address; a fork, or a new home for the project, changes that one line.
- `docs/italian-app-spec.md` — the original build spec (goals, principles, exercise types, spaced repetition, screens), kept for history. Where it disagrees with the content guide, the design system or `docs/exercise-types.md`, they win.
- `docs/design-system.md` — the **Ripasso Italiano** look (Oct 2026): name, logo, colours, type, components and every screen, with mockups, logo files and fonts in `docs/design/`. Follow it for any interface work.
- `docs/italian-app-content-guide.md` — **the standard for all content work**. Every unit, item, explanation and lesson must meet it. Read it in full before touching content.
- `docs/storage-room.md` — where progress is kept and how much room it has (rewritten at v9.26, when saved data moved from localStorage to IndexedDB): the device's room is now gigabytes, so the cloud documents set the room (the largest of the 16 shards is 104 KB at v9.26, under the progress test's 200 KB line: room for about 18,350 more records, roughly eighteen 1,000-card vocab packs); how the move from the old storage works and what the app does when storage fails; going back to an earlier version; and what comes next (more shards when the cloud room runs short, removing the old copy, a native app). Before adding a very big pack, check the room figure the progress test prints (section 8); read this before changing how progress is saved.
- `docs/exercise-types.md` — **the catalogue of exercise types**: every kind of exercise the app builds (from v8.6 also Spot the mistake, Complete the endings, Reply, Sort the words, Match the pairs, Listen and type, Make it plural), when each appears, which units could use the newer ones, ideas not yet built, and the checklist of every place a new type touches. Read it before choosing the mix of items for a unit, and before building a new type; add a row when you add one.
- `CHANGELOG.md` — one line per version, newest first, back to v7.3. Every version adds its line at the top (see How to work).
- `package.json` — the tools' one dependency, Playwright, pinned (the app itself needs nothing; 1.63.0 from 9.27, with Chromium 153). `npm install` once per session where Playwright isn't already installed globally (the tools find it in `node_modules` first, then a global install; in a Claude Code cloud session the global one is already there, with Chromium only, so don't install another), then `npm test` (the runner, `tools/run-tests.js`: every suite, see below), `npm run test:quick` (only what needs no browser, about a minute), `npm run check` (the content check), `npm run test:items -- u19 u17` (the item test on those units; anything after `--` is passed on), `npm run test:verbs`, `npm run test:storage`, `npm run test:rules`, `npm run test:course` or `npm run test:the-tests`.
- `tools/run-tests.js` — the runner behind `npm test` (from 9.27; `node tools/run-tests.js [suite …] [--no-speed] [--no-browser] [--times 5] [--verbose] [--update-counts] [-- arguments for the suites]`). It runs the content check and every suite one after another, each to its end whether or not an earlier one failed, prints the failing checks of any that fail, keeps each suite's whole output in `test-output/` (not committed) and ends with a table of suite, result, number of checks and time (about 17 minutes for everything on a Claude Code cloud session). `--times 5` runs each suite five times in a row and names any check that failed in some runs and passed in others. The suites, in order: check-content, test-reports, test-rules, test-course, test-storage, test-progress, test-ui, test-install, test-speedups, test-sessions, test-choices, test-items `--sample`, test-verbs, test-browsers, test-perf. **`tools/check-counts.json`** records each suite's number of checks: a suite fails here (and on GitHub, which runs each suite through the runner) when it passes with fewer checks than recorded, so a check that quietly stops running is noticed. When a change adds or is meant to remove checks, run the suite through the runner with `--update-counts` and commit the file in the same pull request.
- `tools/test-rules.js` — the rules test (from 9.27; `node tools/test-rules.js`, about six seconds; `--no-browser` for the Node part alone, two seconds). The learning rules case by case, with what each must give written out by hand in the test (never taken from the app's own tables), run against the app's own code in Node with the clock and Math.random fixed: scheduling (`applyResult` and `undoResult` for a grammar word, a flashcard, a Verbs tense and a recognition-only item at every box 0–7, right and wrong, due and not, a first answer and a repeat, recognition and production: the new box, the exact time of the next review and its spread, lapses, lastRight and lastWrong, the day's xp, new items, cards and counts, and undo putting the record and the day back); the streak and the calendar in Europe/Tirane (the goal met exactly, missed today, missed yesterday, a changed goal, the limit on new items resetting at midnight, a session that runs past midnight, the two days the clocks change, a device that changes time zone); and the answer checker (a table of typed answer, accepted answers, options and settings against the result, its note and the closest answer: accents lenient and strict, apostrophes, typos, a slip that makes another word, British and American spelling, contractions, a leading to/the/a, brackets, digits as words, a subject pronoun added or left out, Accept my answer; and, through `answerTyped` itself, that a one-letter slip is forgiven only in the kinds that forgive). Then a few checks in the real app with the clock fixed (Today and Stats across midnight on the day the clocks go back, the same saved progress opened in another time zone). Run it after any change to `applyResult`, `undoResult`, `streak`, `today`, `dayKey`, `newLeftToday`, `checkAnswer`, `answerTyped` or the options an exercise is built with (`typos`, `english`…); when a rule is meant to change, change the table in the test with it.
- `tools/test-course.js` — the course sweep (from 9.27; `node tools/test-course.js`, under a minute, no browser; `--units u01,fc03,vb` for a few). For every item of every grammar unit, vocab pack and the Verbs section, at boxes 0, 1, 3 and 5, four seeded times (310,400 exercises at 9.27): an exercise is built; every answer it accepts passes `checkAnswer` with the options `answerTyped`, `checkTable` and `checkFields` use (the test's copy of those options is compared with what `answerTyped` really hands over); the right option is offered once among at least two, and no wrong option is one the exercise accepts; what is tapped is sound (a mistake to spot is in the sentence, every word to sort has a group, word order offers the sentence's words); for a conjugation and every typed Verbs form, each different form of another person in the same tense is refused; for a flashcard, other cards' answers are refused unless they are the card's own; and nonsense is refused. It fails if far fewer exercises are built than the course has, or a kind is never built. Run it after any change to the content or to how exercises are built or checked.
- `tools/test-the-tests.js` — test the tests (from 9.27; `node tools/test-the-tests.js`, about a quarter of an hour; `--list`, `--only id,id`, `--suite test-ui.js`, `--no-speed`). A list of small faults, each one exact replacement of text in a copy of `index.html`, with the suite that must catch it and words of the check that must fail; it applies each in turn, runs that suite on the copy, and fails if a fault survives, is caught by another check than the one meant, or its text is no longer in `index.html`. It began with the eight faults of the review at 9.26 and has at least one for every suite. Run it after changing a suite, or the code a fault touches (a fault whose text has changed needs writing again); when you add a suite, add a fault for it, and when a bug gets past the suites, add it as a fault once the suite catches it. `.github/workflows/weekly.yml` runs it every Monday.
- `tools/test-browsers.js` — the other-browsers test (from 9.27; `node tools/test-browsers.js`, about ten seconds a browser). In Firefox and WebKit: the app opens, progress an older version left in localStorage is moved to IndexedDB, one whole grammar, Flashcards and Verbs session is completed through the screen, the progress is there after a reload, a backup file is loaded and merged, and the theme is switched, with no script errors. Where neither browser is installed (a Claude Code cloud session has only Chromium) it runs the same checks in Chromium and says so; GitHub runs it with `--require`, which fails without both. Anything that fails only there is a real difference between browsers: report it, don't work round it in the test.
- `tools/lib/` — code the tools share: `load-app.js` loads the app's content into Node, running the storage script first (it finds no IndexedDB there and an empty localStorage) (for check-content, unit-items, add-items, edit-items, check-new-words, pack-levels, same-content, variety, link-sections and test-choices), `content-source.js` finds each content constant in `index.html` and writes it in the one-entry-per-line layout (for format-content, add-items, edit-items and check-content), `browser.js` finds Playwright, serves the app and counts checks, and reads and changes what is saved (`stored`, `save`, `saveText`, `storedRows`: from 9.26 the format of the IndexedDB copy is written out there by hand, and the tests read the database itself with it) (for the browser tests), `node-app.js` runs the app's learning code in Node with a clock the test sets, a seeded Math.random and the real `answerTyped` and `answerOption` with drawing switched off (for test-rules and test-course), `answer.js` answers the exercise on the screen right or wrong by tapping and typing (for test-items and test-browsers), and `seed.js` saves about 6,600 progress records in the page, a well-used device (for test-perf, test-speedups and test-sessions). Change a tool's loading or serving there, not in the tool.
- `.github/ISSUE_TEMPLATE/` — the issue forms reports from the app fill in (from 9.19): `content-problem.yml`, `missing-answer.yml` and `app-problem.yml`, each adding its label (`content`, `missing-answer`, `app`), and `config.yml`. The app opens `…/issues/new?template=<form>&title=…&report=…`, prefilling each form's field by its id, so keep the file names and the field id `report` (`tools/test-reports.js` checks them).
- `tools/read-reports.js` — reads reports from the app (`node tools/read-reports.js reports.txt`, or `-` to paste them in; `--json` for one object per item): the text pasted from GitHub issues, emails or anywhere, in any wrapping. It groups them by item id (following a removed id through `ID_ALIASES`), and prints each report (kind, version, copy, what was shown, expected and given, the note) beside the item as it stands now (one line of JSON, as `edit-items.js --replace` takes it) and its lesson section; app problems follow. See Working through reports below.
- `tools/test-reports.js` — the reports test (`node tools/test-reports.js`, a few seconds, no browser): the app's report text (`reportText`), read back exactly by `read-reports.js` from the app's own text and as it arrives (a GitHub issue, a quoted email, several together); the GitHub address (`issueLink`) for each kind, from a form that exists, filling in only the title and `report`, within 6,000 characters, and with only the title when the report is too long; the email address (`mailLink`); the forms' labels and field ids; and `read-reports.js` on `tools/samples/reports.txt`. Run it after any change to reports.
- `tools/check-content.js` — the content checks (`node tools/check-content.js`, add `--verbose` for every finding), the page's scripts (one app script, one storage script before it, and nothing outside the storage script naming `localStorage`, `sessionStorage` or `indexedDB`, but for the theme snippet's two reads; from 9.26), the Verbs section's example sentences in `VERB_SENTENCES` (from 9.20: each verb in `VERB_GYM`, one sentence for every tense it has, the form as whole words in a row, found by the app's own `vsFind`, the clue in the sentence, British English, 4–9 words, no repeats or copies of grammar-unit sentences, no negative commands; from 9.24 a verb with no sentences at all as a problem; rare words and few persons as worth a look), the lesson links in `ITEM_SECTIONS` (each names exactly one section by its heading, never a number, and every item of a unit with a lesson has one or `null`), that every transform has `en` (the English of its first answer) and every reply `lineEn` (the English of the other person's line), from 9.16, the release notes (`CHANGES` and the version's `CHANGELOG.md` line), and that the content keeps its one-entry-per-line layout. Reads `index.html` and `CHANGELOG.md` and changes nothing.
- `tools/format-content.js` — lays the content constants out one entry per line (`node tools/format-content.js`; `--check` only reports). Safe to rerun: it reads each constant as JSON and writes back the same values in the same order, so on a file already laid out it changes nothing.
- `tools/same-content.js` — checks that two copies of `index.html` hold the same content, however it is laid out (`node tools/same-content.js main`, or two paths or git refs; the second defaults to the `index.html` here). Deep-compares every capitalised content constant (`BUILTIN_PACKS`, `LESSONS`, `VERB_GYM`, `ID_ALIASES`, the tables the exercises use…) and what `buildContent()` makes of them, and lists each difference by its path; `APP_VERSION` and `CHANGES` are not compared. Run it against `main` after any change meant to leave the content alone (a reformat, a change to the tools or the code).
- `tools/variety.js` — the variety report (`node tools/variety.js [u01 …]`, about half a minute): builds every grammar item's exercise with the app's own `makeExercise` at boxes 1–4, eight times each, with a seeded random generator, and prints per unit how many kinds of exercise (`typeKey`) it gives and the shares of the two commonest, flagging fewer than 10 kinds or one kind above 35%, then each kind's share overall. `--markdown` prints the "Measured mix" section of `docs/exercise-types.md`; refresh that section after changing a unit's mix of items.
- `tools/link-sections.js` — proposes, for each item of a unit with a lesson, the section that teaches it (`node tools/link-sections.js [u01 …]`, a few seconds): it scores each section of the item's unit (BM25) by the item's Italian (answers, forms, cloze blanks, fixes), the Italian words of its explanation and its English, and prints the best with a confidence, beside the link stored in `ITEM_SECTIONS`. `--low` lists the proposals to review by hand (confidence under 0.5), `--missing` the items with no link, `--diff` those stored differently, `--json` one object per item, and `--write` stores the proposal for items with no link (never changing a stored one). Its proposals match the hand-reviewed links in `ITEM_SECTIONS` four times in five (nine in ten at a confidence of 0.5 or more, two in three below), so review every proposal under 0.5 by hand, and link to another unit's section where that is where the rule is taught.
- `tools/unit-items.js` — prints a unit's items readably (`node tools/unit-items.js u01`, `--type spot` for one type, `--json` as stored), every card and sentence that uses a word (`--word casa`, with the full data a copy in another unit must match to share progress), and how many items of each type every unit has (`--counts`). Reads `index.html` and changes nothing.
- `tools/add-items.js` — adds new items to `index.html` from a JSON file (`node tools/add-items.js items.json`, `--dry-run` first), each as one line after the last item of its unit, in whichever pack holds the unit (the grammar units, u18 or a vocab pack; not the Verbs section, which is built from `VERB_GYM`); refuses existing ids and anything the app's own pack check rejects. An item of a unit with a lesson needs a `"section"` (the start of the heading of the section that teaches it, `"uXX#…"` for another unit's, or `null`), which it writes to `ITEM_SECTIONS` rather than onto the item. Write new content in a scratch JSON file and add it with this rather than editing the content lines by hand.
- `tools/edit-items.js` — changes and removes existing items: `node tools/edit-items.js --replace items.json` replaces each item by its id, where it stands (each item in full, as it will be stored; refuses unknown ids), (an item may carry `"section"`, its new lesson link) and `--remove ID --to NEWID` deletes an item, with its lesson link, and adds `ID_ALIASES[ID] = NEWID` so its progress moves to NEWID (refuses when NEWID isn't an item; an alias that pointed at ID is pointed at NEWID too). Both take `--dry-run` (which prints the old and new lines), run the app's own pack check and refuse what it rejects, write one item per line, and warn when a change stops an item sharing progress with its copies in other units. Use it rather than editing item lines by hand; afterwards run the content check, the item test on the units changed and the progress test.
- `tools/check-new-words.js` — checks a list of candidate words for a new vocab pack against every word already in the app (`node tools/check-new-words.js words.txt`), so a pack adds only new words. The flashcard packs run from pack 1 (common words) to pack 10 (upper-intermediate), in order of difficulty; a pack's number comes from how common its words are, not from its unit id (pack 2 is unit `fc07`, pack 5 is `fc06`, pack 7 is `fc09`, pack 8 is `fc08`, pack 9 is `fc10`, pack 10 is `fc05`), and each later pack should be a gentle step up.
- `tools/pack-levels.js` — how common each vocab pack's words are (`node tools/pack-levels.js`), the same for a draft list (`… words.txt`), and the most common words no card has yet (`… --missing 1 3000`). It reads `tools/word-ranks.txt`, about 20,000 Italian words in order of frequency, and counts a verb form as its verb and a word cut short or in the plural as its dictionary word (*far*, *caval*, *gocce*). Use it to choose a new pack's words, to number it among the others and to order its cards (other scripts can load its `rankOf`).
- `tools/test-verbs.js` — the Verbs test (from 9.20; `node tools/test-verbs.js`, about two and a half minutes; `--all` for every kind at every box, as it ran until 9.26, eleven to thirteen minutes; `--verbs parlare,andare` for a few verbs, every kind at every box; `--seed N`; `--shard 1/3` for one part of three; needs Playwright and Chromium). test-items doesn't cover the Verbs section; this does: with Math.random seeded and every tense of each verb started, it builds each of the 3,954 verb-tense items' exercises at boxes 0–5 again and again and answers each kind the item can give once, the right way, in the session screen (the New verb card, a whole table, Pick the form, Verb form, From English, Change the tense, Which verb?, Which tense?, Which person?, essere or avere?, Verb in a sentence and Which tense fits?), failing if a right answer is refused or missing from the options, an answer panel lacks the tense's example sentence, a kind is never built or a script error occurs. From 9.27 it also answers each kind wrong once in each tense and requires "Not quite", the right answer shown and an explanation; every exercise at every box is checked without the screen by `tools/test-course.js`. Run it after any change to the Verbs section's code or content (`verbGymExercise`, `vgExplain`, `VERB_GYM`, `VERB_SENTENCES`).
- `tools/test-items.js` — the item test (needs Playwright and Chromium). `node tools/test-items.js u19 [u17 …] [--ids a,b] [--repeats 4]` builds every exercise the named units' items can produce, as new, half-learned and learned items, and answers each one right through the real screen, as a learner would by tapping and typing (a few minutes per unit, longer for a big one; `--repeats 2` is quicker); it fails if a right answer is marked wrong, is missing from the options offered, or a script error occurs. Run it on every unit you add items to. From 9.27 Math.random is seeded (the seed is printed; `--seed N` runs the same exercises again); once for each kind of exercise in each unit the same exercise is also answered wrong through the screen, and must get "Not quite" (a card: "Marked as missed"), the right answer shown and an explanation; `--sample [3]` answers three exercises of every kind in every grammar unit and vocab pack (the run in `npm test` and on GitHub, about two and a half minutes); `--all` answers every item of the course (hours); and `--shard 1/3` runs one part of three.
- `tools/test-progress.js` — the progress safety test (`node tools/test-progress.js`, two or three minutes; needs Playwright and Chromium). Runs the real app in a headless browser and checks that saved progress, in the browser and in the synced copy, survives loading, aliases, practice sessions, syncing and a new device; that a record for every item in the course, moved from localStorage as the app first opens, is saved in IndexedDB, reads back record for record and fits the cloud (each cloud document under the 200 KB line, `CLOUD_LINE` at the top of the test, the limit being 256 KB; from 9.26 the cloud documents set the room, and the test prints how many more records fit under the line: about 18,350 at 9.26, so check that figure before adding a very big pack, and when fewer than 2,000 fit it prints a note pointing to `docs/storage-room.md`; it also prints the size of the saved copy, 3.04 MB, and what the same progress takes in localStorage, where a device without IndexedDB still saves it); that a course far bigger than the old storage could hold still works (section 8b: made-up records take the largest cloud document to about 190 KB, 35,035 records at 9.26, with the app's other keys at their caps; everything is saved, loads back intact after a reload and reaches the cloud; it prints the time of saving one answer with the CPU slowed 4×); that damaged records are repaired or left out in the browser copy, a backup file and the cloud's shards (from 9.4); that only what changed is written to the cloud; and (from 9.19) that a flag's `reportedAt` loads, syncs in the flag's own document and survives a backup and a merge with an older copy, reporting a flag writes only that document, and the problems the app noticed (`itapp.errors.v1`) stay out of progress, the cloud and backups. It reads the database itself, through `tools/lib/browser.js`, where the format is written out by hand. `tools/item-ids.txt` lists every id that may hold progress.
- `tools/test-storage.js` — the storage test (from 9.26; `node tools/test-storage.js`, about a minute; needs Playwright and Chromium, and for its section 9 the tag `v9.25`: `git fetch origin tag v9.25`, or `--old path/to/9.25/index.html`; without it that section is skipped with a note, or with `--require-old`, as GitHub runs it, the test fails). The storage script alone and under the app: values saved, read back and removed, progress in parts and a save writing only the parts that changed; the move from localStorage (every key copied and identical, checked before the switch, the old copy left exactly as it was, made once); an interrupted move (closed in the middle of the copy, and between the copy and the switch, it is made again from the old copy, which stays the live one until the switch; a copy that doesn't match is never switched to); the fallbacks (no IndexedDB: localStorage as before, said on Today and in Your data, and moved when IndexedDB is back; after the move, IndexedDB unavailable, emptied or refusing a save is said plainly and nothing is written anywhere else); one source of truth (after the move the old keys are never written, and read only by the fingerprint check; a change made there by an older version is noticed and merged in when asked); saving (an answer survives the browser being killed once it is saved, and putting the app away writes what was changed without being saved); two windows on one storage (each merges the other's saves, nothing lost or written twice, both moved when they open together, and a window saving the older way moves over once another has made the move); start-up (the theme right before the page body exists, nothing drawn before the saved data is in memory); the version before (updating from 9.25, going back to it and updating again, with a backup file either way); the Storage card; and an old storage filled to the brim. Run it after any change to the storage script, to start-up, to how or when progress is saved, or to `sw.js`.
- `manifest.webmanifest`, `sw.js`, `icons/`, `.nojekyll` — what turns `index.html` into an installable phone app when the repo is served from its own website (GitHub Pages, see below). `sw.js` is the offline worker: it keeps a copy of the app on the device and fetches new versions in the background. It finds a new version by comparing `index.html` itself, so a release needs no change to `sw.js`. When an update is applied it tells every open window, not only the one that asked, and each reloads (from 9.26), so the installed app and a browser tab never carry on in different versions over one storage.
- `tools/test-install.js` — the installed-copy test (`node tools/test-install.js [path/to/index.html]`, about 30 seconds; needs Playwright and Chromium). Serves the repo like GitHub Pages and checks the manifest and icons, opening offline, the update prompt (offered on Today, never mid-session, keeping progress, and reloading a second open window into the new version too; checked on opening, and on coming back only if the last check was over three hours ago), the back button, the backup cards and buttons, and that none of it runs inside claude.ai.
- `tools/test-ui.js` — the interface test (`node tools/test-ui.js`, about three minutes; needs Playwright and Chromium). Tours every screen by tapping, in light and dark at 390 and 360 px wide and at 120% text, and checks the design system's rules: every screen reachable, text that stands out from what is behind it (from 9.27: every piece of text on every screen at least 4.5:1, large text 3:1, from the computed colours), choosing a unit on Units (any card opens with Practise and Read lesson, and Today's Continue card follows the unit practised last), no script errors or outside loads, nothing hidden behind the tab bar, 44 px tap targets, the answer panel, the Appearance setting, the "Lo sapevi?" card, room above the keyboard (on typed questions Don't know and Check must clear a Pixel 8's keyboard, so keep the session screen compact; from 9.20 on every typed Verb in a sentence and Which tense fits?, so keep example sentences and their English short), the exercise types added in v8.6 and the Verbs section's Verb in a sentence and Which tense fits? (9.20), each answered right and wrong by tapping and typing (`newTypes`), English answers with contractions (*I'm* = *I am*), the "What's new" card (shown after the version changes, in every copy, until Got it), Read the rule and Practise this section (from 9.6: when the answer panel offers the rule, the sheet it opens over the session drawn as the lesson draws it, scrolling inside, closed by Close, a tap beside it, Escape and the back button with the session left exactly as it was, links and speakers in it, and the buttons at the end of each lesson section), read aloud (with a stand-in voice: every speaker reads its Italian, a prompt's speaker never gives the answer away on any item, Listen and type plays only the item's own sentence without showing it, and the speakers hide where there is no Italian voice or no speech), and reports (from 9.19, in light and dark at 390 and 360 px and at 120% text, with `window.open` replaced so a report link opens nothing: Report it after Flag this item, Suggest it for everyone after Accept my answer, each flag's Report beside Remove, Report all, Suggest and Suggest all, the problems the app noticed with Report and Clear, Report an app problem, the learning summary's Copy and Save as a text file, and the You rows to them; ## How the app reaches Grant

The app reaches Grant in two ways, both from the same `index.html`:

1. **The claude.ai artifact** (https://claude.ai/artifact/1d1Zqo9n8UtXgizSuxjVnJ), with cloud sync. After work here is merged, Grant republishes `index.html` to that link from a claude.ai chat.
2. **The installed copy** (from version 8.1): GitHub Pages serves the `main` branch at https://grantgilford.github.io/ripasso-italiano/, and Grant installs it on his Android phone from Chrome. **Merging to `main` publishes it**: the installed app finds the new `index.html` the next time it opens and offers it on Today ("Update now"). Its progress is kept on the device only (no cloud sync), with backup files to move it between copies.

So:

- Never try to publish or deploy anything yourself, and don't merge to `main`. Your job ends with a tested `index.html` on a branch.
- `index.html` must keep working as a single self-contained file, both on claude.ai and opened straight from disk. Don't split it into several files, add a build step, or load anything except pinned scripts from cdnjs. The files beside it (manifest, worker, icons) are only for the installed copy, and the app only uses them when served from its own website (`HOSTED` in the code: outside claude.ai, over https or on localhost). Inside claude.ai (`IN_CLAUDE`) none of the installed-copy code runs: no manifest, no worker, no history entries, no notices.
- Outside claude.ai the Android back button is handled with one extra history entry while away from Today (`syncHistory()`); in a session, back asks before leaving. A new screen with a header back arrow (`screenHead(…, { back })`) is handled automatically.
- **Progress is kept in two places, and both hold Grant's real progress:**
  - **The browser copy**, in IndexedDB from 9.26 (database `ripasso`, one table `data` of JSON texts by key), read and written only through `Store`, the storage script in `<head>`: `Store.get(key)`, `Store.set(key, value)`, `Store.remove(key)`. The keys are the ones localStorage had, and each small value is one row under its key; progress is kept in parts under `itapp.progress.v1/…` (`head`, `days_YYYY`, and the records in buckets `b000`–`b255` by a hash of the item id), so a save writes only the parts that changed, and the storage's own rows are `store.migration` (the move) and `store.rev` (a token, new with every save). On a device that had progress before 9.26 the move is made once, as the app first opens, and checked before the switch; the `itapp.*` keys in localStorage are then never written again and stay as the copy from before the move (merged in only when asked, in Your data › Storage). One key in localStorage is still written, `ripasso.boot.v1` (`{ theme, idb }`: the theme for the first paint, and the time of the move, which tells a start where IndexedDB won't open that the data lives there). Where IndexedDB can't be used and the data has never been moved, `Store` saves in localStorage exactly as before 9.26. The keys: `itapp.progress.v1` (progress), `itapp.packs.v1` (imported packs), `itapp.reading.v1` (last lesson section read) and `itapp.migratedV1` (a one-time flag). `itapp.theme.v1` (Appearance: `"light"`, `"dark"` or `"auto"`) is a per-device preference, deliberately kept out of progress so it never syncs; the small script in `<head>` paints with it before the app starts (from the note `ripasso.boot.v1`, which `Store` keeps in step with it). `itapp.backup.v1` (`{ at, snooze, welcomed }`: the last backup made on this device, the backup reminder's snooze, and whether the first-run card was dismissed) is per-device too and never synced, as is `itapp.audio.v1` (Read aloud: `"off"`, `"normal"` or `"slow"`; from v8.2), since each phone has its own voices, `itapp.seen.v1` (the `APP_VERSION` whose "What's new" card this device has dismissed, as a string such as `"9.1"`; from v9.1; a device with no progress yet starts with the current version, so a first visit gets no card), and `itapp.lasttype.v1` (from v9.5: the kind of exercise, `typeKey`, each grammar item was last answered with on this device, as a list of `[record id, typeKey]` pairs, oldest first, at most 2,000; the session uses it to give the item another kind next time), and `itapp.confusions.v1` (from v9.7: pairs of items mixed up on this device, as a list of `[record id, record id, times]`, the two ids in order, the pair mixed up last at the end, at most 500; meaning choices offer the other word first and the answer panel says "You've mixed up X and Y N times" from the second time), and `itapp.errors.v1` (from v9.19: the script errors and unhandled rejections noticed on this device, as a list of `{ m: message, at: place in the code, screen, v: version, t: time, n: times in a row }`, oldest first, at most 20, noted by the small start-up script before the app's own, so an error while the app starts is kept too, and saved through `Store` once the saved data is in memory; Your data lists them as Problems the app noticed, to report or clear; never synced, never in a backup and never sent unless reported). A flag (`progress.flags`, synced as `flags/<id>`) may carry `reportedAt` (from v9.19, the time it was reported, shown on Your data as "Reported on <date>"), an optional field older copies keep without reading.
  - **The synced copy**, in the artifact's cloud database (`window.claude.use("db")`), which carries progress across devices: `progress2/meta`, `progress2/days_YYYY`, the item shards `progress2/s00`…`s15` (each record packed as a fixed-order array), plus `flags/<id>` and `packs/<id>`. The old `progress/main` document is still read once per device for migration.

  Saved data is in memory once `Store.ready` is kept, and the app starts then (`boot()`): nothing before it may read or save, and nothing may be saved before `STARTED` is set (an empty progress saved over the real one would remove it). `saveProgress()` hands progress to `Store.set`, which finds the records that differ from what is stored and writes their buckets, the head and the year's log in one transaction, at once; a save that fails says so later (`Store.onError`, which sets `S.saveFailed`). As the app is put away or closed (`putAway()`), every part is compared with what is stored and written if it differs. When another window of the app has saved (the installed app and a browser tab share the storage), `Store` reads the storage again and calls `Store.onChange` with that window's progress, which is merged as the cloud's is (`adoptRemote`) and saved; there (`adoptRemote(theirs, true)`, from 9.27) a day that differs only in how it is written is taken as the other window wrote it, so the two windows settle on one form and stop writing (the storage test checks that they do). Never read or write `localStorage` or `indexedDB` outside the storage script (`check-content.js` reports it), and never write the old `itapp.*` keys in localStorage after the move.

  The counts on Today, Units, Stats and You are kept between visits (`counts()`, from 9.3) until `saveProgress()` or `buildContent()` drops them or time changes one, so code that changes progress must go on calling `saveProgress()` afterwards (as all of it does), or those screens show the numbers from before. From 9.4 it must also mark what it changed for the cloud (`DIRTY`): `markItem(id)` for a record, `markDay(day)` for the daily log (`today()` marks it for whoever asks), and `saveProgress()` marks meta; code that replaces progress wholesale sets `DIRTY = null`, so the next push compares every document. An unmarked change still reaches the cloud, but only when the app is put away (that push compares everything). Every record read from storage (the browser copy, a backup, the cloud's shards, either side of a merge) goes through `checkRec`, which repairs or drops a damaged one; keep it that way for any new way in. Word lists and indexes taken from the content (`KNOWN_WORDS`, `GLOSS`, the search index, from 9.6 `SECTIONS`, each item's lesson section, and from 9.7 `NEAR`, the forms word order traps are found with, and `ANSWERS`, every word's Italian for the confusion memory) are built while the phone is idle; their `*Steps` generators must yield after each small step so no slice runs over 50 ms (`test-perf.js` measures it). `CONTEXT` (9.7, the grammar units' sentences by word, for the flashcard sentences) is built when a card first needs one instead, held to the same 50 ms, and `VS_INDEX` (9.20, each verb-tense item's example sentences from `VERB_SENTENCES`, with where its form stands in each) is worked out an item at a time when first needed; `buildContent()` drops them all when the content changes.

  Never rename a key, collection or document, change the shard count or hashing, reorder the packed record, change the browser copy's parts (their names, the 256 buckets or their hashing) or the database's name, table or version, or otherwise change either format without a migration that reads the old format (the browser copy's is written out by hand in `tools/lib/browser.js`, the cloud's in `tools/test-progress.js`; update them in the same branch as the migration). The two copies are merged on every load, so a change to one must keep the merge with the other working, and a mistake in either loses progress on every device. When an item is removed or renamed, map its old id in `ID_ALIASES`.

## How to work

1. Work on a new branch, never directly on `main`. Grant reviews and merges.
2. Bump `APP_VERSION` (7.2 → 7.3, and so on) for any change that will be republished, and update the version mentioned in the content guide's first paragraph if the guide changes. Every version also says what changed, twice: replace `CHANGES` beside `APP_VERSION` with this version's changes in one or two plain sentences for Grant (Today shows them once, as "What's new"), and add the version's line at the top of `CHANGELOG.md` (`- **9.2** (date): …`). `check-content.js` reports a problem until both are done.
3. **Run the whole of `npm test` before finishing, every time** (about 17 minutes; where Playwright isn't installed, `npm install` first). It runs the content check and every suite to the end and finishes with a table; every suite must pass, and the content check must report no problems (read its "worth a look" list and deal with anything your change added). If the table says a suite has fewer checks than recorded, a check has stopped running: find out why before touching `tools/check-counts.json`. While working, a quicker run of the suite that covers what you are changing saves time (the list below is only a guide for that, not a replacement for the whole run): `npm run test:quick` (a minute, no browser: the content check, reports, the rules and the course sweep) after any change to content or to how exercises are built or checked; the interface, `tools/test-ui.js`; navigation, backups, the installed-copy code or the files beside `index.html`, `tools/test-install.js`; search, the counts, the Verbs reference or idle-time work, `tools/test-speedups.js`; how sessions are built, scheduling, the summary or Stats, `tools/test-sessions.js` and `tools/test-rules.js`; the answer checker, `tools/test-rules.js`; wrong options, the confusion memory, flashcard sentences or the answer panel's reasons, `tools/test-choices.js`; reports, `tools/test-reports.js` and `tools/test-ui.js`; the storage script, start-up, how or when progress is saved, or `sw.js`, `tools/test-storage.js` and `tools/test-progress.js`; the Verbs section, `tools/test-verbs.js --verbs` on the verbs you changed. If you add items, run `node tools/test-items.js` on the units you added them to, and run the progress test with `--update-ids` to add their ids to `tools/item-ids.txt`; if the progress test reports a missing id, an item was removed or renamed without an `ID_ALIASES` entry, so add one rather than editing the list. After a change meant to leave the content alone (to the tools, the code or the layout), also run `node tools/same-content.js main`: it must find no difference. If you deliberately change a storage format, write the migration first and then update the test to the new format in the same branch. After changing a suite, or code that `tools/test-the-tests.js` has a fault for, run that too. Where a check isn't scripted yet, add it to these scripts (or a new one under `tools/`), with a fault for it in `tools/test-the-tests.js`, and commit it, so the next session can reuse it. Once the branch is pushed and a pull request is open, GitHub runs the same suites (`checks.yml`); if a job fails there, fix it.

   **What needs no browser** (Node alone, nothing to install, about a minute in all: `npm run test:quick`): `node tools/check-content.js`, `node tools/test-reports.js`, `node tools/test-rules.js --no-browser`, `node tools/test-course.js`, and `node tools/same-content.js main`. ## Working through reports

Anyone using Ripasso can report a problem from the app (from 9.19), and nothing leaves their device unless they tap. Reports reach the project as GitHub issues, made from the forms in `.github/ISSUE_TEMPLATE/` and labelled `content` (a flagged item), `missing-answer` (an answer accepted with Accept my answer, suggested for everyone) or `app` (something that looks or works wrong, with the script errors the app noticed); or as text pasted from an email or a copy. Each holds one or more plain-text reports, each starting with the line `Ripasso report 1`. Issues are public: a report holds the exercise, the answers, the learner's note, the version, which copy (installed, browser or claude.ai) and, for an app problem, the browser and the errors, and never progress, settings or anything about the person. To work through them, as any maintainer:

1. **Gather them.** Copy the reports from the open issues (or the emails) into a scratch file and run `node tools/read-reports.js that.txt`. It groups them by item (following a removed id through `ID_ALIASES`) and prints each beside the item as it stands now and its lesson section. Several reports on one item usually point at one real problem.
2. **Check each one against `docs/italian-app-content-guide.md`**, the item as it stands now (it may have changed since the version in the report) and its lesson section. Decide whether the item is wrong or the learner was. Either fix it, or reply on the issue saying why the item is right, in plain words, and close it; where a learner's slip shows that an explanation or a wrong option's note could be clearer, improve that instead.
3. **A content problem** (`content`): fix the item with `tools/edit-items.js --replace` (never by hand), keeping to the guide: a right answer marked wrong usually means a missing alternative (in `it`, `answer`, `fix` or the cloze), and a wrong explanation or note is fixed in the item and, where it says the same, in the lesson. Then run the content check, the item test on the unit and the progress test, as for any content change.
4. **A missing answer** (`missing-answer`): add it only after checking in a dictionary (Collins, Oxford, Cambridge or Treccani) that it translates the card in the sense the card means, and only where it isn't already accepted some other way (a leading *to*, *the* or *a*, an American spelling or a contraction are accepted already). Add it to the card's `en` in the guide's form: British spelling, after the existing glosses, with a bracket where the English word has several senses. An answer sent from Your data comes as the app stores it, in small letters, without a leading *to*, *the* or *a*, and with some British spellings in their American form (*color*), so write it back in its natural British form. If it isn't right, reply with the dictionary's sense and close the issue.
5. **An app problem** (`app`): the report gives the version, the copy, the browser and the screen, and each error with its place in that version's `index.html` (`index.html:LINE:COLUMN`; check out the version's tag, `vX.Y`, to read the same line). Reproduce it, fix it, and add a check to the test that covers that part of the app, so it stays fixed.
6. **Close the issues with the fix.** Put `Fixes #N` in the commit message or the pull request description (`Fixes #12, fixes #15` for several), so merging to `main` closes each issue; reply on any issue closed without a change, saying why.
7. As for any change: a new branch, `APP_VERSION`, `CHANGES` and the changelog line, and the checks.

## Writing style

British English throughout, as the content guide sets out. Plain, concise explanations. Grant is learning Italian at roughly A1–A2 level and isn't a programmer: summaries for him should be in plain language.

## Safety net

The tag `v7.2` marks the known-good starting version. From 9.1 every version that reaches `main` gets its own tag (`v9.1`, `v9.2`…, made by `release.yml`), so `index.html` at any released version can be restored. If anything goes wrong, return to the last good version's tag, or to `v7.2`.
